# Image generation and safe upgrades

Image routing is independent of the text LLM. Settings > Image Provider selects a
default and optional thumbnail, inline, portrait and standalone-design overrides.
The OpenAI GPT Image provider supports `gpt-image-2`, `gpt-image-2.5-sunburst` and
`gpt-image-2.5-flare`. The UI explicitly saves medium quality; requests use PNG,
1024x1024 portraits and 1536x1024 landscape images. Operation configuration can
specify low, medium or high quality. Prices vary with model, quality and usage.
The text-only image adapter records returned input/output tokens for cost estimates;
pricing is configurable through the existing pricing settings. Provider billing is
authoritative. Missing usage metadata cannot provide a reliable cost estimate.

Legacy `dalle` configuration is preserved but blocked with actionable guidance.
An administrator must explicitly choose and save a replacement. No automatic
provider, model, quality or credential migration occurs. Imagen remains supported.
Unknown provider/model selections fail rather than silently selecting another.

## Explicit actions and automation

Creating writers or completing onboarding no longer generates paid portraits.
Use the explicit Generate Avatar control. Manual article/bulk/inline/portrait and
designer actions may incur provider charges, even with `AUTOMATION_ENABLED=false`.
Article concepts can require an additional text-generation call. Inline requests
return their actual outcomes synchronously; allow enough HTTP timeout for multiple
image calls. GPT Image has a 180-second per-image timeout. A timed-out request may
still have incurred charges; it is not automatically retried. Explicit HTTP 429
rejections can be retried by the job queue. There is no provider fallback.

With automation disabled, publication does not enqueue thumbnails and the scheduled
worker remains disabled. Existing queued work is preserved. Enabling automation is
a separate operator decision; this change does not enable it. `db.init()` creates
the missing jobs table and indexes idempotently for fresh/existing installations.
Skipped existing/archived/missing articles are recorded as no-ops, provider failures
are failures, and stale recoveries consume retry attempts.

## Persistence and rollback

Generated bytes must have a valid PNG signature and stay within 20 MiB. Replacement
uses unique storage keys and an atomic compare-and-swap database update. The old
pointer and asset remain until successful persistence. Concurrent updates cause a
conflict instead of overwriting another editor's selection. Inline failures retain
the previous image for each affected position. Ambiguous database failures retain
the new asset too, since the update may have committed; this can leave an orphan
for later deliberate cleanup. Remote legacy assets are retained conservatively.

Back up the application database/media before a separately approved deployment.
The jobs schema is additive: keep the table during source rollback to avoid losing
queued/history records. Roll back code/images without dropping job or image data.
This PR does not deploy or migrate any running database, change saved providers,
enable automation, or perform paid image tests. Actual provider access/quality and
reverse-proxy timeout behavior require a separately authorized live test.
